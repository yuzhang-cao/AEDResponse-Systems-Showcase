# 网格索引计算范围实测

日期：2026-09-13。对象：本项目当前未提交源码。问题：地理网格是否真正缩小招募计算范围，还是实际业务仍对全体用户计算距离。

## 结论

**网格本身有效，部分业务路径有效；事件首次创建、定时补招、接受请求仍对远方用户执行距离计算。** 因此当前不能称为“整个招募流程已按地理分区局部计算”。

位置更新的距离筛选已局部化，但整个请求仍可能因 outbox 的旧事务而重建全部设备索引；距离计算局部化与请求整体成本局部化应分别验收。

## 实验方法与边界

- 固定 3 名近处响应候选，另有 1 个患者 iPhone 与 1 个 Watch。
- 仅增加远方的合成用户：0、250、1,000；近处用户、事件、操作顺序保持一致。总设备数分别为 5、255、1,005。
- 两种存储均执行：`MemoryStateStore` 和新建临时数据库的 `SQLiteStateStore`。
- 每个组合依次执行 7 个阶段：网格查询加精确筛选、全扫对照、事件创建、响应者位置更新、tick、附近人数查询、接受请求。共 42 个阶段观测。
- 直接调用当前业务服务，未经过 HTTP、真实身份供应商或线上服务器；这项实验回答计算范围，不是公网性能或容量测试。
- 在源码临时副本中，只给 `distanceMeters` 与网格查询/重建循环加计数，不修改返回值或业务分支。分别统计总距离调用、包含远方位置的调用、网格访问和重建设备访问。
- 关闭开发期 shadow 全量对照，保留原有其他检查；防止把诊断性的双算误认成正式主路径的计算。
- 用完全未修改的项目源码运行相同场景作对照。42 个阶段的业务结果和原有成本计数全部一致；全部 42 个后端源文件运行前后 SHA-256 不变。
- Node v24.18.0。计数插桩会增加执行开销，因此本文不报告或推断生产延迟、QPS、容量。

所有数据均为合成数据；临时 SQLite 库已关闭并删除。业务代码未修改、未部署、未操作生产库、未发送真实通知。

## 实际距离计算次数

下面是单次操作中 `distanceMeters` 的调用次数。Memory 与 SQLite 两组结果完全相同。

| 路径 | 远方 0 人 | 远方 250 人 | 远方 1,000 人 |
| --- | ---: | ---: | ---: |
| 网格查询后精确筛选 | **3** | **3** | **3** |
| 全量距离计算（对照） | 3 | 253 | 1,003 |
| 创建患者事件 | **24** | **1,024** | **4,024** |
| 响应者位置更新 | **11** | **11** | **11** |
| 定时补招 tick | **9** | **509** | **2,009** |
| 附近人数查询 | **2** | **2** | **2** |
| 接受响应请求 | **11** | **761** | **3,011** |

直接查询网格在本场景固定访问 16 个格、返回 3 个设备；增加远方用户不影响这个集合。其精确筛选结果与全量距离计算相同。

额外单独统计“输入中包含远方位置”的距离函数调用，确认增长确实来自远方用户：

| 实际业务路径 | 加入 1,000 名远方用户后的远方位置计算次数 |
| --- | ---: |
| 创建患者事件 | 4,000 |
| 定时补招 | 2,000 |
| 接受响应请求 | 3,000 |
| 响应者位置更新 | 0 |
| 附近人数查询 | 0 |

这些次数是本合成场景的累计调用，不是不同用户人数，也不是所有真实场景固定不变的系数。所有情况下首次创建事件都只向同样的 3 名近处用户生成邀请，远方用户不会被错误招募，但仍可能浪费筛选计算。

## 为什么会出现部分有效

1. [DevicePositionIndex]([PROJECT_ROOT]/backend/src/device-position-index.ts:50) 已维护网格与设备归属；位置更新可以增量迁移网格，查询只遍历相关格。
2. [TxRecruitmentContext]([PROJECT_ROOT]/backend/src/tx-recruitment-context.ts:183) 查询附近格，再合并事务内设备变化，因此响应者位置更新的招募筛选已用上索引。
3. [旧候选适配器]([PROJECT_ROOT]/backend/src/recruitment-context.ts:305) 仍直接 `Object.values(state.devices)`。
4. [事件创建]([PROJECT_ROOT]/backend/src/service.ts:2330)、[tick]([PROJECT_ROOT]/backend/src/service.ts:2724) 和接受后的招募刷新仍使用旧适配器。这不是只有文件名或测试代码存在的问题，实际调用计数已验证。

## 整个请求还有全量工作

以 SQLite 的“响应者位置更新”阶段为例：

| 指标 | 远方 0 人 | 远方 250 人 | 远方 1,000 人 |
| --- | ---: | ---: | ---: |
| 距离函数调用 | 11 | 11 | 11 |
| 全量状态 clone 次数 | 10 | 10 | 10 |
| 网格重建设备访问总次数 | 20 | 1,020 | 4,020 |

clone 次数相同不代表复制的数据量相同。该场景中待发通知的处理仍通过 [outbox 旧事务]([PROJECT_ROOT]/backend/src/notification-outbox.ts:163)；SQLite 的旧事务提交后会 [全量重建位置索引]([PROJECT_ROOT]/backend/src/store.ts:1802)。所以主招募筛选已局部化，后处理仍处理全体设备。

附近人数查询也仍有一次全量状态 clone。本文没有把这些内存复制或索引重建统计成“距离计算”，两种成本分别列明。

## 正确性检查

- 网格结果经过精确距离筛选后，与全量对照一致。
- 增加远方用户后，邀请对象、附近人数和接受后的任务结果不变。
- 用户移出/移回网格，索引成员正确更新：Memory/SQLite 各 3 组通过。
- 位于相邻网格、相距约 2 米的点，在 10 米查询中不会因为网格边界漏掉。
- SQLite 关闭重开后恢复相同的网格成员：3 组通过。
- 上述辅助正确性检查共 10 项，在插桩与未插桩两次运行均通过。
- 项目原有 `device-position-index`、`recruitment-run-metrics`、`responder-position-transaction` 三组测试 **27/27 通过**。它们通过不表示所有业务入口已迁移；本轮调用计数已经显示未迁移的入口。

## 应如何收尾

- 将事件创建、定时补招、接受/退出后的招募刷新等剩余入口接入同一套支持事务内变化的地理候选查询，保持原业务规则。
- 只读取招募半径覆盖的格及必要邻格，再精确筛选，不能只查患者所在单格。
- 维护位置新增、移动、失效、删除及事务回滚的索引一致性；不能直接把已提交索引中的旧对象当成事务中的最新状态。
- 去掉请求后处理中的不必要全量事务、clone 与全量索引重建。
- 验收分别检查：远方用户数量变化不增加本地招募的远方距离计算；索引维护与状态读写的整体成本也不因无关用户线性扩大。

本轮只验证，没有实施上述改造，也没有重新引入已取消的 2 万在线目标。
