# 后端容量压测报告（2026-09-11）

对 Azure 联调后端 `aedresponse-server`（Japan East）实施的实测压测，回答"这台服务器能承受多少用户"。
全部数字来自本机实测，非推算的地方已标注；推算式结论单独列出并给出依据。

- **被测对象**：线上 `aedresponse.service`（真实进程、真实 `state.sqlite`、真实 Caddy HTTPS 入口）
- **压测方式**：负载生成器运行在同一台 VM 上，直连 `127.0.0.1:8787`；另用 Mac 经公网 HTTPS 做对照
- **时间**：2026-09-11 12:41–13:10 UTC
- **压测机选择说明**：用户首选 Windows PC（Tailscale），实测 Windows 离线（最后在线 21 小时前）、本机 Tailscale 亦离线，故按用户指示回退为"服务器本机生成负载"

## 结论速览

| 问题 | 实测答案 |
| --- | --- |
| 这台服务器能承受多少**同时在线待命用户** | **约 600 人**（自洽上限：此时写容量 100% 用于记录待命位置，零余量）；留出事件/读取余量后**实际约 250–500 人** |
| 能承受多少**事件参与者** | **约 40–60 人**同时在线参与（若同时还有待命用户则更少） |
| 写事务硬上限（当前数据量） | **~10 次/秒**，与并发数完全无关 |
| 新建 Socket 连接上限 | **~10 条/秒**（每次连接 = 一次写事务） |
| REST p95 ≤ 500 ms 在几并发下破 | **4 个并发客户端**（p99 在 2 并发即破 1000 ms） |
| 20 万注册 / 2 万在线 / 800 RPS / 4000 msg/s 的 P20 目标 | **不可达**：即使空库，写上限也只有目标的 1/80；达到承载 2 万用户所需的数据量后差距放大到 4 个数量级 |

## 2. 根因：每次写事务都是全量状态操作

`SQLiteStateStore.transact`（`src/store.ts:1399-1415`）对**每一次**写执行：

```
cloneState(全量深拷贝) → mutation → validateState(全量 Zod 校验)
  → assertAppendOnlyHistory(全量) → persistChanges(全量 flatten + diff) → 单队列串行提交
```

`store.read`（读路径）同样做 `cloneState` 全量深拷贝。

在**压测前**的库上（955 实体 / 1.42 MB）分相实测：

| 阶段 | 中位耗时 |
| --- | --- |
| `cloneState`（全量深拷贝） | 6.06 ms |
| `validateState` + `assertAppendOnlyHistory` + 深比较 | **40.15 ms** |
| flatten + diff + SQLite 提交（no-op） | ~0 ms |
| **一次 no-op 事务合计** | **45–59 ms** |

即：**每次写有 40/45 的成本花在"校验整个数据库"上**，与被修改的数据无关。

| 端点 | 状态访问 | 顺序吞吐 | p50 | p95 |

| `GET /healthz` | 无 | **853 /s** | 0.65 ms | 1.52 ms |
| `GET /api/v2/events` | **全量事务**（`tick()`） | **9.8 /s** | 91.8 ms | 173.8 ms |
| `GET /api/v2/me/presence` | **全量事务**（`tick()`） | **6.1 /s** | 151.3 ms | 232.3 ms |
| `GET /api/v2/aeds` | 全量克隆 | 86.3 /s | 10.4 ms | 15.3 ms |
| `GET /api/v2/me/nearby-volunteers` | 全量克隆 | 86.2 /s | 10.7 ms | 15.3 ms |
| `PUT /api/v2/me/responder-position` | **全量事务** | **10.7 /s** | 87.4 ms | 163.9 ms |
| `PUT /api/v2/me/presence` | **全量事务** | **13.1 /s** | 73.9 ms | 131.2 ms |

两个关键设计问题由此暴露：

1. **`GET /api/v2/events` 与 `GET /api/v2/me/presence` 是"写"**。两者都调用 `service.tick()`，而 `tick()` 内含 `store.transact()`（`src/service.ts:2435`）。客户端每轮询一次事件列表，就产生一次全量状态写事务。
2. **纯读端点也是 O(全量状态)**。`listAeds`（`service.ts:4025`）与 `getNearbyVolunteerSummary`（`service.ts:2621`）都用 `store.read` → 每次调用克隆整个数据库。

## 4. 并发饱和：吞吐量与并发数完全无关

`GET /api/v2/events`（全量事务路径），每档 20 秒：

| 并发 C | 吞吐 RPS | p50 | p95 | p99 | 服务端 CPU |
| --- | --- | --- | --- | --- | --- |
| 1 | 9.72 | 93 ms | 180 ms | 182 ms | 1.46 cores |
| 2 | 9.78 | 187 ms | 364 ms | 368 ms | 1.46 cores |
| 4 | 9.73 | 372 ms | **741 ms** | **754 ms** | 1.46 cores |
| 8 | 10.03 | 743 ms | 1478 ms | 1493 ms | 1.46 cores |
| 16 | 9.90 | 1584 ms | 1794 ms | 1921 ms | 1.44 cores |
| 32 | 10.27 | 3088 ms | 3166 ms | 3169 ms | — |
| 64 | 9.96 | 1590 ms | 25088 ms | 26289 ms | — |
| 128 | 12.27（64 个失败） | 6177 ms | 18445 ms | 20041 ms | — |

**吞吐量从 C=1 到 C=64 恒定在 ~10 RPS**，延迟随并发线性增长。这是单写者队列 + 全量校验造成的硬串行瓶颈，增加客户端并发不会提高吞吐，只会排队。

- **SLO 拐点**：REST p95 ≤ 500 ms 在 **C=2 通过（364 ms）、C=4 失败（741 ms）**；p99 ≤ 1000 ms 在 C=2 通过、C=4 失败。
- 服务端 CPU 饱和在 **~1.45 cores**（JS 主线程跑满），不是 CPU 数量不够，而是工作无法并行。

作为对照，**不触碰状态的 `/healthz` 达到 6,715–6,866 RPS**（C=64…256，p50 8–33 ms，0 错误）。
所以瓶颈**完全在存储层，不在 HTTP/传输层**。

## 7. Socket.IO 连接能力

| 目标连接数 | 成功 | 失败 | **连接速率** | p50 建连 | 服务端 RSS |
| --- | --- | --- | --- | --- | --- |
| 50 | 50 | 0 | **9.9 /s** | 2,347 ms | 135 MB |
| 200 | 200 | 0 | **10.1 /s** | 9,461 ms | 139 MB |
| 500 | 209 | **291** | **10.1 /s** | 20,000 ms（超时） | 148 MB |

建连速率与写事务上限（~10/s）**完全一致**，原因是 `touchDevice` 在每次 Socket 连接时执行一次 `store.transact`（`src/service.ts:2695-2702`）。首次鉴权 `authenticateToken` 也走全量读。

推论：

- **2 万条连接仅建立就需要 ≥ 33 分钟**，且期间服务无法处理其他业务；
- 一次 App 前后台切换/网络抖动的批量重连（500 条并发）**实测 58% 失败**；
- 连接内存约 30–65 KB/条（本机测点较少，仅作量级参考）。

## 8. 换算："能承受多少用户"

口径（本文档显式冻结，因 `docs/requirements.md` 未定义"同时在线"）：
**"同时在线" = 已建立并通过鉴权的 Socket.IO 连接，且保持待命心跳的 iPhone 设备。**

流量模型取自需求：

- 待命用户：**每 120 秒或移动 100 米**上报一次最新 R（`requirements.md:45`）→ **0.00833 事务/秒/人**
- 事件参与者：**每秒一个秒槽、每 5 槽一批**（`requirements.md:47-48`）→ **0.2 事务/秒/人 = 待命用户的 24 倍**

**自洽解**：设 U 个待命用户在线，其自身写入需求为 U/120 事务/s；服务端在该数据量下的容量实测为 `容量(U) = 1000 / cost(U)` 事务/s，其中 `cost(U) = a + b·U`（毫秒）由第 5 节数据线性拟合。令两者相等：

```
U / 120 = 1000 / (a + b·U)      →      b·U² + a·U − 120000 = 0
```

| 拟合参数 | a (ms) | b (ms/用户) | 解得的 U |
| --- | --- | --- | --- |
| 由 (54, 101 ms) 与 (10504, 2439 ms) 两点拟合 | 88.9 | 0.2237 | **≈ 560** |
| 较乐观的一组 | 60 | 0.21 | **≈ 626** |

即 **~560–630 人**，本文取 **~600**。两组参数结论一致，说明数量级不依赖拟合细节。
（该线性拟合相对第 5 节实测在中段偏高，因此 560 这一端更接近真实。）

| 场景 | 实测支撑的上限 |
| --- | --- |
| 纯待命用户，服务只做位置记录 | **~600 人**（此时写容量已 100% 占用，零余量） |
| 含任何事件/读取/重连流量 | **~250–500 人** |
| 纯事件参与者（无待命流量） | **~40–60 人** |
| 新建连接风暴容忍度 | **~10 条/秒** |
| 当前数据量下满足 p95 ≤ 500 ms | **≤ 2 个并发业务请求** |

## 9. 与冻结的 P20 目标对比

`docs/requirements.md:172` 冻结目标：20 万注册 / 2 万同时在线 / 100 并发事件 / 2,000 参与者 / 800 REST RPS / 4,000 Socket msg/s，持续 60 分钟。

| 目标项 | 实测 | 差距 |
| --- | --- | --- |
| 800 REST RPS | **~10 事务/s**（空库时；2,504 用户时 1.9/s） | **80× 起，实测规模下 ~400×** |
| 2 万同时在线 | 建连 10 条/s → 需 33 分钟 | 且期间不能做别的 |
| 2,000 事件参与者 | ~40–60 人 | **~40×** |
| 4,000 Socket msg/s | 未单独压测；但每次广播都要 `reconcile()` 遍历全部连接（`realtime-access.ts:50-59`），O(连接数) | 结构性不满足 |
| 20 万注册用户 | 单事务外推 ~9 秒 | 不可用 |

**结论：当前单进程 SQLite 参考实现不支持 P20 目标，且差距不是调参能弥补的**——这与 `docs/connectivity-repair-2026-09-08.md:41`「20万用户/2万在线/60分钟验收没有通过证明」的既有判断一致，但现在有了量化证据。

## 10. 对生产架构的含义（按性价比排序）

1. **`GET /events` / `GET /me/presence` 不应触发 `tick()` 写事务**。把 `tick` 改为定时器驱动（例如 1 秒一次），读路径变成纯读，可立即消除最大的一类写放大。
2. **`touchDevice` 不应每次连接都开事务**。改为内存心跳 + 周期性批量落盘，可把建连上限从 10/s 提到数千/s。
3. **校验/克隆必须改为按实体增量**。当前 40/45 ms 花在全库校验上；只校验被改动的实体是数量级改善。
4. **读端点去掉全量 `cloneState`**（`listAeds`、`getNearbyVolunteerSummary`）。
5. **`sendToDevices` 的 `reconcile()` 是 O(连接数)**，广播前不应全量重算授权；应改为按连接缓存 + 撤销事件驱动。
6. 长期路径仍是需求已冻结的 **PostgreSQL/PostGIS + Redis 兼容缓存 + 持久队列**；本压测为迁移必要性提供了量化依据。

## 11. 本次压测的边界与未覆盖

- 未压测**事件进行中**的真实负载（100 并发事件、招募扩圈、状态确认、通知广播），因为没有可用的事件创建入口（受控模拟事件入口当前未启用白名单）。第 4 节的 400 batch/s 推算取自评审稿的"设计推断"，非实测。
- 未测 **Watch 备用上传**、APNs、离线重试风暴。
- 未测 **60 分钟长稳**（内存/句柄增长）——10,504 用户档的 RSS 306–343 MB 未触上限，但只跑了数十秒。
- Socket 内存/连接是**每令牌多连接**的上限式测试（50 个令牌开 500 条），单设备单连接的真实场景下速率上限相同。
- 公网路径对照：从 Mac（中国）经 HTTPS 到 Japan East，200 并发实测 **~572 RPS、p50 75 ms（RTT 主导）、0 错误**；该链路是本机到 Azure 的瓶颈，不能用于测服务器上限。所有容量数字均来自本机回环。
- 负载生成器与被测进程**共享同一 2 vCPU**，因此上述数字是**偏保守的下界**（生成器约占用 0.2–0.5 core）。反过来说，真实独立压测机上测得的绝对上限会略高，但串行瓶颈的性质不变。
