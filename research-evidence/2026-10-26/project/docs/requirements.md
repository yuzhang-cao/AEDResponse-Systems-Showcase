# AEDResponse v2 需求与验收基线

状态：全部产品规则已于 2026-09-05 确认并进入开发。本文是 v2 的 canonical 产品与验收基线；与旧版、旧聊天或现有代码冲突时，以本文为准。外部服务商密钥、Apple entitlement、生产域名和云资源属于部署配置，不改变已冻结的业务语义。

## 首次使用与身份

2026-09-08 开发安排补充：正式流程恢复开发，测试源码保留；通过构建开关
`AED_ENABLE_TEST_FEATURES` 控制，当前测试 Debug 构建开启，正式构建/Release
关闭。未登录页面只保留正式 Sign in with Apple 入口（2026-09-13 起手机号入口已移除），
测试会话说明仅为可折叠辅助
区域，不取代正式登录；真实身份不得被残留测试导入覆盖。外部服务未配置时
明确不可用，不返回假成功。见 [本批进度](formal-flow-progress-2026-09-08.md)。

1. 生产 App 必须登录，只允许一种入口：Sign in with Apple。不得提供密码、游客、匿名、邮箱、微信或其他登录方式，也不再提供手机号验证码入口（2026-09-13 用户决定移除；`/auth/phone/*` 路由、短信 provider 端口与相关契约一并删除）。每个已验证凭据映射到后端稳定 `userId`，账号键为 (provider, subject) 且从不自动合并不同 subject。账号绑定能力若后续需要，另行确认后再开发。
2. 首次运行顺序固定为 `登录 → 四项协议与同意 → 必要权限 → 主界面`。在登录、患者协议、志愿响应者协议、隐私政策、敏感个人信息单独同意任一项缺失或版本失效时，只显示相应门禁；不激活 WCSession，不请求定位/通知，不连接 REST/Socket.IO，不启动 Watch 业务监控，也不进入任何业务界面。用户不签署时自行关闭 App，不调用私有或不安全的进程退出 API。
3. 位置权限必须为 `Always` 且开启精确位置，通知权限必须可用；只授予 `When In Use`、关闭精确位置或拒绝通知时不提供待命和救助服务。Watch App 单独申请定位与 Fall Detection 授权。
4. 登录成功后，后端签发限权、短期、可撤销且可轮换的设备会话；凭据存入 Keychain，不得硬编码、记录到日志或展示给用户。业务设备、Watch 绑定和事件参与记录必须关联稳定 `userId`，不能再以可重装生成的匿名设备 ID 作为唯一用户身份。
5. Sign in with Apple 的 identity token 必须由后端验证签名、issuer、audience、expiry 和 nonce；不得信任客户端提交的 Apple subject。Apple subject 只以加盐不可逆摘要持久化。生产环境没有配置 Apple 验证器时必须 fail closed，任何测试验证器只能存在于显式测试依赖中。
6. Watch 不提供独立登录表单。已登录 iPhone 通过 WCSession 传递一次性、短时、只用于绑定的 companion ticket；Watch 自身设备证明通过后绑定到同一 `userId`。ticket 不授予位置上传或事件创建权限，退出登录或解除配对会撤销绑定及 Watch 会话。
7. 用户通常处于 `NEUTRAL`。本人 Watch 事件关联到该用户后自动成为 `PATIENT`；附近用户进入响应请求界面，接受后才成为 `RESPONDER`。同一用户在同一时刻只有一个运行身份，优先级固定为 `PATIENT > RESPONDER > NEUTRAL`。
8. 独立 `AEDResponseTestHost` 的 Debug 构建可以用显式 fake auth 和本地 fixture 预览登录、患者/响应者 UI，但必须明确标识、强制断开后端，且不得编译进生产 target 或 Release。

## Watch / iPhone / 后端隔离

- Watch App 只监控 Apple Watch 系统 Fall Detection、App 自有的“是否需要帮助”回答和 Watch 上可观察到的外拨状态，保留稳定事件 ID/时间并直报后端。正常情况下 Watch 只携带触发时位置快照；当 iPhone 不能通过 WatchConnectivity 即时到达且 Watch 自身存在广域网连接时，Watch 允许立即开始备份上传。后端连续 10 秒未收到有效 iPhone P 后才把 Watch 切为有效来源；任一有效 iPhone P 到达立即恢复 `IPHONE_PRIMARY`。Watch 绝不主动拨号、编排响应者或选择 AED。
- iPhone App 不导入或调用 `CMFallDetectionManager`，不通过 iPhone CallKit 决定触发；它从后端接收事件并负责 UI、地图、导航、响应决定、任务和 AED 协同，同时作为手机当前位置的网络上报端。
- 后端是 Watch 与 iPhone 的业务隔离边界。Watch 重复回调、App 重启重放、REST 重试和 Socket.IO 重复消息都必须按稳定 ID 幂等去重。
- 附近匹配由服务器完成：待命/搜索圈 iPhone 通过 latest-only 接口上报 R；成为患者或接受响应后，iPhone 切换到事件级严格秒槽批次，其中 P/R `FIX` 同时更新最新位置投影。后端按位置时效、精度和可配置半径定向发送请求；不使用 Apple 设备间蓝牙作为业务传输。active patient 不得同时发布或使用 R 身份。
- watchOS companion 使用现代单 target Watch App。`CMFallDetectionManager` 需要 `NSFallDetectionUsageDescription`、用户授权和 Apple 单独批准的 `com.apple.developer.health.fall-detection` entitlement；Xcode 登录 Apple 账号不等于已获批准。

## 设备位置与可参与状态

- 生产 iPhone 与中国大陆境内生产后端之间的业务数据必须走公网可达的 HTTPS REST + WSS Socket.IO。关闭 Wi-Fi 后，iPhone 必须能够仅通过蜂窝数据持续上报 R/P、接收事件与任务；也必须支持任意外部 Wi-Fi。不得要求 iPhone 与 Windows 位于同一局域网、同一网段或加入 Tailscale，不实现蓝牙业务协议。
- 生产客户端使用可配置的公网域名，不硬编码个人 IP；必须执行系统正常的 TLS 证书校验，不得通过关闭证书校验、接受自签名证书或明文 HTTP 绕过。`http://127.0.0.1` 或受控私网 HTTP 只允许用于开发测试，不构成生产或广域网验收证据。
- Windows/SQLite 只是本地开发与经审核真机联调的参考后端，不是生产真相源站；原始 Node.js HTTP/Socket.IO 端口不得直接裸露公网。生产入口必须终止受信任 TLS、支持 WebSocket upgrade，并在进入境内 Node.js 应用集群前提供访问控制、已冻结的异常熔断、请求大小限制与审计；不得对正常位置频率另加业务限流。具体生产云资源仍须用户审核后才能创建。
- 待命/搜索圈 iPhone 幂等提交强类型 latest-only `ResponderPosition (R)`；与 active event 关联的患者和已接受响应者仅通过事件批次提交强类型 P/R。单条 `/events/{eventId}/patient-position` 仅保留为过渡兼容接口，生产 iPhone 不与批次双写。每次上报携带稳定幂等 ID、客户端采样时间和必填精度；服务端记录接收时间并拒绝旧样本覆盖新样本。
- iPhone P 是患者态的首选与正常来源。Watch 对 iPhone 可用性的近端判定使用 WatchConnectivity：只有 `activationState=ACTIVATED && isReachable=true` 禁止备份上传；`ACTIVATED + false`、`INACTIVE`、`NOT_ACTIVATED` 均可在 Watch 自身有 WAN 时立即备份上传。`isReachable` 只表示当前 live messaging，不证明 iPhone 是否能经蜂窝/Wi-Fi访问后端，所以后端仍以“连续 10 秒无有效 iPhone P”作为最终来源切换条件。Watch fallback 首次立即发送，此后每 5 秒或累计移动 10 米提前发送。任一当前有效 iPhone P 到达立即恢复 `IPHONE_PRIMARY`；较旧请求不得倒退 fix，同时间或更旧的 Watch 样本不得覆盖。来源切换不改变或结束事件。
- 非事件状态下若 iPhone 不可达且 Watch 无 WAN，用户状态直接标记 `UNAVAILABLE_NO_CONNECTIVITY`，Watch 只提醒一次，不循环骚扰。Fall 上下文或事件进行中不运行这套待命失效提示流程，也不能因为断网自动结束事件。
- 后端按已登录用户与设备保存：`userId`、认证方式索引、device/session 关联、最新 P/R、精度、客户端发生时间、服务端接收时间、`lastSeen`、协议状态、通知/定位能力、可参与状态、当前事件和任务。普通管理员不可查看 Apple subject 或精确位置。
- 当前 SQLite 仅作为本地参考实现；生产目标迁移至中国大陆部署的 PostgreSQL + PostGIS，Redis 兼容缓存承担短时 presence/房间/幂等热点，持久队列承担通知与延迟任务。附近资格仍以服务端 canonical 地理计算为准，客户端距离只供展示。
- “附近可参与”至少需同时满足：已签志愿响应者协议、通知与定位能力可用、R 位置有效且未过期、在半径内、当前可用、不是患者本人、没有冲突的 active assignment。半径、新鲜度与精度上限均为可配置边界；恰好等于边界时合格，超过边界时排除。
- 新鲜度使用服务端当前时间减去已验证的客户端 `observedAt`；处于允许时钟偏差内的轻微未来时间按 age=0 处理，超过配置偏差的未来样本拒绝。`lastSeen` 或重试不能让旧坐标重新变新。presence 更新也按稳定 ID 与 `occurredAt` latest-wins；bootstrap 只初始化缺失状态，轮换 session 不覆盖更新的 presence。

### 位置采集、上传与留存分级

- 普通待命用户：iPhone 按 120 秒或移动 100 米触发最新 R 更新；只保留最新位置，不形成轨迹档案。
- 事件搜索圈内但尚未接受的用户：仅新增进入当前搜索圈的用户提高到 15 秒或移动 30 米；事件过程中已覆盖的圈不回缩。
- 患者与已接受响应者：iPhone 对服务端授权参与窗口内的每个合法 UTC 整秒槽严格产生且仅产生一条位置事实。有合格的真实 Core Location fix 时记为 `FIX`；同秒回调多个合格 fix 时，只有在该秒槽尚未提交时才可以用观测时间更晚的 fix 替换本地草稿。某秒没有新 fix 时仍必须记录 `NO_NEW_FIX`，不得复制上一坐标伪造 1 Hz fix。
- 五个连续秒槽组成一个正常 REST 批次；累计移动达到 10 米时可提前提交当前 1—4 条连续秒槽并重新开窗。一个批次首次发起提交时，其中的 `recordId`、`slotAt`、状态、fix 时间和坐标就在本地永久封口；后续只能原样重试，不得 correction、补改或用迟到 fix 替换。REST ACK 只表示服务端已持久化并允许客户端删除该重试副本，不是封口时点。若后续 REST 权威参与窗口证明一个未 ACK 批次跨越边界，客户端可仅重组传输分批：合法记录的 `recordId` 和全部内容必须保持不变，越界记录必须进入 append-only 隔离证据，不得删除或伪造修正。
- 参与事件的位置事实按秒保存；离线时加密排队，服务端 REST ACK 前不得删除。App 重启恢复时先等待最多 5 秒接收系统补交的历史 fix；此前进程已观测但无 fix 的槽记 `NO_FIX`，确认属于进程未运行期间且仍缺 fix 的槽记 `APP_NOT_RUNNING`。Watch 仅在患者 iPhone 不可用时承担事件位置采集；非事件 Watch 仍可采集最新位置，但只保留一个最新值。
- 每个位置批次最多 5 个记录且批内秒槽必须连续；恢复联网后可按原批次乱序重试，不合并成超大 payload。到达顺序不能被当成缺秒；当前参考后端尚无 `stream-finalized`/`sync-complete` 信号，不得在正常写请求中把跨批次临时缺口固化为最终审计结论；最终全参与窗口核对需后续显式完成信号或留存截止审计任务。验收标准是每个合法秒槽恰好一条记录；合法秒槽内存在至少一个合格真实 OS fix 时不得错误记为缺口，同秒只保留首次提交前观测时间最晚的合格 fix；其他空缺均须有原因。完整参与 60 秒必须有 60 条秒槽记录，但不要求有 60 个新坐标。
- 服务端只在批次最后一个秒槽已经完整结束时落库；尚未结束或客户端快钟的秒槽返回可重试 `425 Too Early`，不保存任何记录。这保证未来位置证据不能阻塞患者的急救优先结束操作。

### 动态招募范围

- 目标有效接受人数固定为 3。初始半径 1 公里；若合格候选少于 3 人立即扩到 1.5 公里，仍不足再扩到 2 公里。
- 候选数量达到 3 但 30 秒内有效接受不足 3 人时，同样按 1 → 1.5 → 2 公里扩圈。只通知新增环带用户并提高其定位频率；已展开半径在本事件内不缩小。
- 达到 2 公里后不再因人数不足阻塞救助，按实际接受人数 N 进入分配，同时继续补招。

### 中立待命的附近人数展示（2026-09-06 补充）

- 用户确认这里的“响应者”指附近待命、可以接受救助请求的其他用户，不是正在救助事件中的人员；此展示不改变 `NEUTRAL` 身份，也不自动发起事件或招募。
- 同时提供列表和地图视图，进入时默认列表。暂沿用现有 1、1.5、2 公里范围，列表为“1 公里内 N 人”等累计人数；同一个用户在较大范围内重复包含，不能将各行相加。
- 后端以查看者已保存的有效最新 R 为中心，按协议、定位/通知能力、可参与状态、位置时效/精度与活动事件状态筛选；排除本人所有设备、当前患者和已接受参与中的用户，以稳定用户身份去重。
- 只下发统计时间和三个范围人数，不下发被统计者的姓名、联系方式、设备/用户标识、精确坐标、轨迹、任务信息或个人距离。地图用查看者自己的位置和范围圈层展示，不绘制个人点位。
- 无有效位置、服务不可达、未获有效统计或缓存过期时显示“附近人数暂不可用”，不得用 0 人替代未知；0 人只能来自成功的统计结果。展示缓存 120 秒失效，不改变原有位置采样/上传频率；进入待命页或用户下拉时刷新，不新增后台高频轮询。
- TestHost 仅使用明确标注“示例数据”的本地汇总；离线地图是范围示意图，不访问地图服务。真实模式的 MapKit 范围地图和真实聚合接口仍需后续独立网络验收。
- 本次实机测试的连接限制已由用户更新为“有线无线无所谓，直接开始”；可使用实际可用链路执行离线 TestHost 验证，并如实记录 transport。不能把有线测试称为纯蓝牙或无线验证。未恢复授权的服务器接收、真实登录、蜂窝公网和物理 Watch 测试继续暂停。

## 严格触发语义

1. `CMFallDetectionManager` 是生产跌倒信号来源；App 不用自制加速度算法替代 Apple 严重摔倒判断，也不拨打或取消系统急救电话。
2. 收到 Fall 回调后，App 保存最多 120 秒的最小 Fall 上下文并显示自己的单次询问：“是否需要帮助？”该询问不取代 Apple 系统提示。
3. 用户回答“需要帮助”时立即成立事件，不要求先观察到外拨；回答“不需要帮助”时本次事件不成立。未回答时，只有在 Fall 后 120 秒内首次观察到新的 outgoing call 才成立事件。
4. 外拨路径不等待接通、不判断号码、不累计时长。`CXCallObserver` 不提供号码，因而 App 不能证明拨打的是 120；也不能检测系统是否已向紧急联系人发送摔倒与位置消息。除非后续找到经批准的替代信号，否则保持上述规则。
5. 上报包含稳定 `eventId`、`fallDetectedAt`、Apple `fallResolution`、`appHelpResponse=NEEDS_HELP|NO_RESPONSE`、可选 `callFirstObservedAt`、位置与精度。`callFirstObservedAt` 是 App 首次观察时间，不是系统权威拨号时间。
6. 触发上报失败进入受保护 outbox；从 Fall 起超过 35 分钟不得创建迟到事件。按2026-09-09本轮明确整改要求，未确认原观察不能因截止时间而删除：超期先查询已存在事件，再用原正文重放确认；GET不等于原内容ACK。服务端匹配ID/有效状态ACK后，同次本地原子写入保留恢复事件ID并删除重试正文；已确认/拒绝问答的最小去重标记仍按24小时。内容拒绝保留原观察并暂停自动写入，未知/无权限记录不能被当作已终态或新事件。不得保存原始传感器、健康数据或连续位置。
7. 后端对首次有效上报创建 `ACTIVE/RECRUITING` 事件，患者 iPhone 自动进入患者界面并立即持续上报 P。Watch 触发快照只在首个 iPhone P 前或满足 10 秒仲裁后作为有效 P。服务端取得有效 P 后开始动态扩圈招募。

## 响应与 AED 协同

- 候选人在接受前只收到通用通知；完成认证后最多看到任务类型、距离区间/ETA、当前招募半径和 30 秒有效期。不得显示患者精确坐标、地址、姓名或其他身份信息。
- 接受后，同事件响应者之间只显示随机匿名编号、任务角色、状态、近似位置图标和 App 内联系能力；不显示姓名、头像、原始手机号、邮箱、精确坐标、历史轨迹或个人 ETA。患者只看聚合人数与下列自动播报，不查看志愿者个人信息。
- 只有明确接受请求的设备计入有效响应人数 `N`；拒绝、超时和仅收到通知的设备不计入。
- 有效 `N` 在事件结束前包含仍参与的已接受设备；`TIMED_OUT`/`CANCELLED` 将其移出，`AED_UNAVAILABLE` 只触发重派而不退出，已完成任务仍保留为事件参与者。若 N 降低后已开始或已获取 AED 的锁定任务超过公式目标，安全优先保留这些任务；其余未开始任务和新接受者按缺口确定性补位。
- AED 目标人数为 `round(N/3)`，资源充足时患者方向人数为 `N - AED人数`，采用普通四舍五入（`.5` 向上）；资源不足按下述急救优先规则降级，不得为凑齐公式人数而拒绝响应者：

| N | GO_TO_PATIENT | FETCH_AED |
| --- | --- | --- |
| 1 | 1 | 0 |
| 2 | 1 | 1 |
| 3 | 2 | 1 |
| 4 | 3 | 1 |
| 5 | 3 | 2 |

- 任务角色只允许 `GO_TO_PATIENT` 和 `FETCH_AED`；服务端在有效人数变化时以 REST 状态真相重新计算并广播任务。新增接受者按当前角色数量缺口补位，已开始行动或已获取 AED 的任务不得无故换角色。
- 2026-10-08 用户更新：AED 初次分配和退出补位按响应者 `R → A → P` 两段实际步行路线的总距离排序，不再计入预计时间、固定步速或楼层/门禁/核验耗时。对可补位响应者和可用 AED 的候选组合优先选择总距离更短者；同分时使用稳定规则去重。未开始任务可直接补位，在途改道仍须 15 秒明确确认。
- `FETCH_AED` 路线必须严格为 `R → A → P`，保留开放时间、设备可用性、占用和不可用报告检查；楼层、门禁等资产信息保留，但其耗时不参与距离排序。
- 最新决定：手机 MapKit 分别查询 `R→A` 和 `A→P`，取返回步行方案中的最短距离并上报；后端确认分配。每轮预筛最多八个附近候选，结果只保证已返回候选中的距离排序。取消旧 `detour ≤ 300 秒` 限制，算路失败不使用直线距离冒充实际路线。导航检测高德安装状态，优先高德，否则 Apple；高德唤起失败回退 Apple。无需地图 Web API Key。原始 WGS-84 定位保留为事实，两个地图按取 AED/去患者阶段导航。
- 对实际接受人数 N，`round(N/3)` 名响应者并行获取互不相同的 AED，其余前往患者；每名 AED 响应者一次只获取一台。可用 AED 不足时立即使用现有资源、记录缺口，其余人员前往患者并继续搜索，不等待资源齐全。
- 无 AED 特例（2026-09-05 用户补充）：在既定查找范围及可用性条件下没有可分配 AED 时，所有新接受的志愿响应者均分配 `GO_TO_PATIENT`，直接前往患者处；不得因 AED 缺失拒绝接受、等待 AED 或强行分配 `FETCH_AED`。已有已开始或已取得 AED 的锁定任务仍按原安全规则处理，本条不改变查找范围。
- 到达 AED 后提交幂等 `AED_ACQUIRED` 回执，至少包含 `receiptId`、`eventId`、`assignmentId`、`aedId`、`acquiredAt`。服务端按 `receiptId` 和业务三元组去重，并实时同步所有参与者，防止重复获取。
- 保留 `AED_UNAVAILABLE` 和重派；已获取的同一 AED 不再分配给其他响应者。若其他前往患者的响应者顺路可取替代 AED，后端可提出改道，但必须由该响应者在 15 秒内明确确认，超时保持原任务，禁止静默改派。
- offer 超时为 30 秒。事件参与设备连续 15 秒没有有效数据标记 `COMMUNICATION_UNCERTAIN`；连续 30 秒标记 `COMMUNICATION_LOST` 并补位。两种状态只追加事实和触发调度，不删除历史、不证明人员真实失联，也不自动结束事件。
- 当前 AED 响应者退出时优先当面交接；双方各确认一次。无法当面交接时，可用 App 内相机拍摄一张同时包含 AED 与固定明显标识的照片，并记录 30 秒内、精度不超过 50 米的当前位置。禁止相册选择，不做 AI/后台语义审核；JPEG 最长边 2048、单张不超过 5 MiB、剥离 EXIF、存入私有对象存储。只有位置和照片均成功后才生成临时 AED 任务，后续获派者临时可见并确认“找到/未找到”。
- 服务端实时同步附近候选/已接受人数、offer、接受/拒绝、任务创建/变化、到达、`AED_ACQUIRED`、`AED_UNAVAILABLE`、误报撤销与事件完成。完整状态仍以 REST 为准。
- 患者地址/楼层/入口卡片是可选的服务端 enrichment，不得阻塞基于有效 P 坐标的 offer；没有 enrichment 时客户端仍使用 P 导航。

## 误报、恢复与结束

- 外拨前系统误报取消不会创建后端事件。
- 患者使用两个独立按钮（2026-09-06 用户修订）：“误报”用于意外触发、实际不需要救助，记录为误报取消；“结束救助”用于患者已经得到救助，记录为救助结束。两个操作各明确确认一次，停止本事件相关志愿任务，已有事件证据完整保留；误报不能记成成功救助。App 不取消 Apple 系统电话。到场响应者报告“专业急救已接管”仍使用独立语义。
- 患者“取消救助”（2026-09-13 用户修订）单独使用三次确认，结果为 `ASSISTANCE_WITHDRAWN` / `CANCELLED_ASSISTANCE_WITHDRAWN`。前两次不发送结束请求，关闭或事件变化从头开始；服务端确认后停止本次协作并保留既有记录。
- Watch 恢复动作、心率恢复、紧急电话结束、网络断开或 Watch 暂时失联均属于被动观察，绝不自动结束患者或救援状态。
- 到场响应者可以用一次确认报告“专业急救已接管”。响应者主动退出后立即失去患者位置、团队位置和事件通信权限，并以稳定 `userId` 永久禁止重新加入同一事件。
- 响应者退出确认（2026-09-13 用户修订）：所有主动退出均需三次明确确认；其中唯一响应者仍需额外强调其唯一身份。原特例说明：若当前事件只有本人这一名仍参与的已接受响应者，提示“你是当前任务唯一一名响应者，确定要退出吗。”，必须由用户连续明确确认 **3 次**后才提交退出操作。点击退出入口本身不计为一次确认；三个确认步骤分别标明 1/3、2/3、3/3，任何一步取消或关闭提示均不退出，重新发起时从 1/3 开始。待接受、拒绝、超时、已退出者及同账号其他设备不得被误算成另一名响应者。未完成第三次确认前不提前撤销当前任务或权限。本条不增加患者结束救助和到场响应者报告专业急救接管的确认次数。
- 唯一响应者完成确认后允许退出，不要求等待替补；N 降为 0 时记录退出与无人响应事实、按既有规则提示患者并继续补招，不能因无人响应自动结束事件。若退出后仍有其他响应者，继续按人数变化补齐任务缺口并保留锁定任务；对在途人员的 AED 改道仍须按原规则明确确认。三次退出确认不替代其他响应者的改道确认，也不替代已取得 AED 的交接流程。
- 结束与退出请求中的客户端时间只是声明，原声明保留用于幂等指纹。业务状态使用 `max(min(clientClaimedAt, serverReceivedAt), causalLowerBound)` 得到服务端权威时间；患者或响应者手机慢钟不得导致一次确认失败，快钟也不得扩大位置证据窗口。
- 事件开始 30 分钟仍未终结时，后端发送一次状态确认“救助是否仍在进行”；用户选择继续后重新开始 30 分钟周期。5 分钟内无人回答时，在 T+35 分钟立即置为 `CLOSED_UNCONFIRMED_NO_RESPONSE` 并完整记录，不能标记为成功解决。
- 除患者/到场响应者明确操作、上述 T+35 无响应规则或依法授权的后台流程外，电话结束、App 关闭、权限变化、网络断开、无响应者和单纯经过时间都不得结束事件。
- 事件终态生效后，服务端广播终态；患者和所有响应者 iPhone 立即清除 active 任务/导航、恢复待命 R 上报，但保留事件审计 timeline。
- iPhone 不自动拨号。可以保留用户主动点击、由系统处理的号码快捷按钮，但它不参与触发语义。

## 不变量

- `PatientPosition (P)`、`ResponderPosition (R)`、`AedPosition (A)` 保持强类型，禁止用通用坐标替代。
- 患者有效 P 必须同时公开来源与仲裁状态：`IPHONE_PRIMARY` 优先于 `WATCH_FALLBACK`，触发快照为 `WATCH_TRIGGER_SNAPSHOT`。来源切换不能改变事件身份，也不能自动结束事件。
- REST 是状态真相；Socket.IO 只做低延迟通知，重连后必须 REST 对账。
- iPhone 在蜂窝数据、Wi-Fi、无网状态之间切换时，不得创建重复事件或让旧位置倒退；连接恢复后必须重新建立 HTTPS/WSS 会话，并先通过 REST 恢复状态真相，再继续位置写入与任务操作。
- Socket 断线重连后，iPhone 必须先拉取当前未完成 event、delivery/assignment（2026-09-09 整改：恢复改用有权限的结构化快照，内部 append-only 审计仍保存，不能对外直返），完成角色恢复后才继续位置上报与任务操作。
- 时间线只追加，仅用于后端状态对账与审计，不向患者或响应者展示；通知、响应、AED 回执与 Watch 上报均幂等。
- 只收集完成协同所需的最少位置、时间、设备会话和任务数据。

## 数据最小化、证据与用户权利

- 非事件待命位置只保留最新值，服务器收到新值即替换旧值；超过 10 分钟或用户撤回/停用服务时物理删除。事件参与者 1 Hz 位置批次、状态、回执、消息与媒体属于事件证据，事件发生后不得由普通业务删除或覆盖。
- 完整事件原始数据前 30 天处于受限在线层；第 31 天至 3 年进入中国大陆境内的加密封存层；满 3 年删除精确轨迹、照片、消息和设备关联，只保留不可逆聚合统计。依法 `legal hold` 只冻结相关事件并记录依据。
- 账户操作（2026-09-13 用户最新修订）：活动救助仅由手机端拦截退出登录和注销；先完成三次确认的取消/退出救助。未参与时退出登录在本机立即完成并停止采集，保留持久队列补发远端撤销，不等待服务器许可。注销通知服务器将 `users.lifecycleState` 改为 `CLOSED` 并记 `closedAt`；服务器保留既有信息和注销标记，所有相关会话失效。设备登录另记 `SIGNED_IN/SIGNED_OUT`，不把未登录当成注销。注销回执保留 request ID 和状态；备份恢复必须重放关闭/撤权标记。原“注销自动物理删除非事件数据”的承诺作废，按用户要求改为逻辑状态关闭。
- 普通用户不能导出、下载或分享任何事件数据。只可申请查看与自己有关的数据：后端验证登录身份、设备生物识别/密码与签名挑战后，在 15 个工作日内批准最多 24 小时的只读视图；仍不得查看他人隐私。法院、监管或正式执法请求走独立合法流程且限定单一事件。
- 事件证据使用 append-only 序号、前一条 hash、当前 SHA-256、媒体/批次 hash 和终态 manifest/服务器签名。修正以新记录追加，不原地修改；该机制只能证明系统记录未被篡改，不能证明现实事实绝对真实，不使用区块链。
- 安全日志保留 6 个月且不含敏感 body；业务数据访问审计保留 3 年。每日加密备份在中国大陆境内滚动保留 30 天，照片位于私有对象存储。

## 后端最小可见与外部披露

- 自动化服务用 `userId` 和事件 ID 处理精确数据。普通管理员界面不显示手机号、Apple subject、患者精确位置或照片；紧急 break-glass 仅限单一事件、只读、MFA、必须填写原因、最长 30 分钟并全量审计。
- APNs payload 只含不透明 ID 与通用提示，不携带位置、身份或医疗描述；敏感 body 不进入日志。
- 当前不向 120、医院、警方、物业或其他外部人员自动披露。Apple Emergency SOS 独立于本 App；未来正式官方接口需要另行需求、法律与安全审批。

## 消息、流量与异常保护

- 所有业务写入统一走 REST；Socket.IO 与 APNs 只用于低延迟通知和触发客户端 REST 对账，不保留 Socket 写路径。
- 每个非媒体 REST JSON 文档和每个 Socket.IO 事件最大 16 KiB；16,384 字节接受，16,385 字节返回 `413`。位置批次最多 5 条，6 条返回 `422`。照片独立最大 5 MiB，不计入 JSON 上限；消息只传 `photoRef`。
- 正常按冻结频率上传不做业务限流。仅当同一已认证设备每秒超过 5 次位置写并持续 10 秒时启用 30 秒异常熔断：期间最多每秒接受一个最新批次，多余返回 `429`；事件确认、退出和 AED 状态接口始终保持可用。超限 Socket 消息忽略并由 REST 对账。
