# G13-A 第一批整改独立复核

日期：2026-09-13。依据当前工作树与本轮实际执行；未读取其他聊天，未修改业务代码、提交、部署或连接生产库。用户已取消原 2 万在线目标，本文只审查计算范围。

## 结论

事件创建的**距离筛选确实接入网格**，固定 3 名近处响应者时，远方用户增加到 1,000 仍只有 24 次距离调用，邀请对象与顺序不变。但 G13-A 整体不能验收：候选构造仍多次枚举全部设备，而且这次共享函数重构给原本有效的位置事务路径增加了全设备扫描。应先修复候选查询，再迁移 tick。

## 已确认的问题

### 1. 共享候选查询增加了位置事务路径的全量工作

[tx-recruitment-context.ts]([PROJECT_ROOT]/backend/src/tx-recruitment-context.ts:187) 每次调用无条件执行 `tx.keys("devices")`；构造参数时还无条件执行 `tx.keysWhere("devices", ...)`，即使已经提供 `deviceIdsForIdentity`，该扫描仍会发生。参数求值并不会因为 helper 最后选择身份索引而省略。

[candidateDeviceKeys]([PROJECT_ROOT]/backend/src/recruitment-context.ts:339) 又遍历整个 `orderedDeviceKeys` 建 ordinal Map。原事务适配器直接查询现有 `deviceOrdinal`；只有缺少身份/顺序索引时才全扫。现在提供了索引也无法避免这些扫描。

在隔离副本中仅恢复上一版事务适配器，位置请求的全设备 key 枚举和 committed 设备谓词检查均从 `15/765/3,015` 恢复为 `0/0/0`，业务结果保持一致。此项是本轮新增的计算范围回退，不能只归入原有 outbox 开销。

### 2. 事件创建的“候选访问 40”没有覆盖构造候选集的全量扫描

[draft 适配器]([PROJECT_ROOT]/backend/src/recruitment-context.ts:405) 先 `Object.keys(state.devices)`，再过滤全部设备寻找患者同账号设备，随后 helper 再遍历所有 key 建顺序表。只有最终返回的局部候选才计入 `deviceCandidatesVisited`。

因此“候选访问恒定”成立，“整个候选构造已局部化”不成立。现有 `recruitment-scope-g13a.test.ts` 能守住邀请集合和最终候选数，不能阻止这类隐藏全扫。

本轮测试覆盖 Memory/临时 SQLite、7 类操作、跨格移出移回、相邻格及 SQLite 重开。插桩副本、未插桩当前代码、仅恢复旧事务适配器的对照各产生 42 条操作记录、10 项正确性检查；三组业务输出逐项一致。当前 42 个后端源文件的 SHA-256 在运行后仍一致。这里只通过 service 调用执行真实 tick/outbox，没有把它描述为隔离 HTTP 路由全覆盖，也没有验收所有 G13-A 边界。

## 建议整改顺序与验收

1. **先修共享候选查询。** 保留共享资格规则；利用现有 `deviceOrdinal`、`deviceIdsForIdentity`，将全设备 key 获取和身份扫描改为仅在无索引时惰性执行。合并当前事务 staged 设备并从事务视图取值，保留顺序与去重。补上 key 枚举/谓词检查计数，要求有索引的正常路径不扫描远方设备。
2. **再迁移 tick 补招。** 处理到期/受影响的活动事件，避免每秒复制全状态后遍历全部历史事件。迁移涉及状态确认、扩圈、过期、改派与通知，不能只替换一处 context。每个事务的 delivery、assignment 与位置变化都必须即时可见。
3. **补齐其他入口。** 接受/退出、患者位置/事件批次、presence 变化，以及患者优先导致的旧事件补招逐条验证。事件首次触发的简单场景通过，不代表这些组合也通过。
4. **缩小同次请求的后处理。** outbox、响应投影、状态读取与索引维护改为按变化实体和相关通知处理，消除正常请求的全状态 clone/位置索引重建。
5. **按清单整体验收。** 保持 1/1.5/2 km 与扩圈时序、业务结果、稳定顺序；覆盖事务内新增/移动/删除、失效、回滚、重开和隔离 HTTP + tick/outbox。分别记录距离调用、候选数、全 key 遍历、clone 和索引重建，不以任一计数代替整体结论。
