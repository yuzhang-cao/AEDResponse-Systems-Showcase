审查日期：2026-09-09

## 2. 总体评价

这份文档没有明显把目标架构冒充当前实现：它明确写出当前为原生 iPhone/Watch、集中式单进程后端和 SQLite 状态存储，并承认 APNs、部分正式身份依赖、目标路线能力及容量验证尚未完成。业务状态、参与关系、位置事实与 UI 投影的区分也有价值。（原稿 L427–487、L518–524、L838–853）

但它主要回答了“目前代码被作者理解为怎样运行”，还没有完整回答“这些行为哪些已经批准、哪些符合原始需求、哪些必须改变、改变后如何验收”。因此应当区分三种结论：

| 评审对象 | 本次结论 |
| --- | --- |
| 当前业务与代码组织的梳理稿 | 可以继续作为评审输入，但代码事实仍须对应源码复核 |
| 已批准的业务规则与可执行目标设计 | 暂不冻结；存在未决规则、未闭合路径和外部能力前提 |
| 正式运行、容量或上线验收 | 现有材料不能支持通过；静态说明及文件哈希不是运行证据 |

## 3. 应优先处理的发现

### RV-01 无回答自动关闭：必须单独作为关键业务决策

**原稿事实。** 事件 30 分钟时进入状态确认，5 分钟没有有效继续回答便进入 `CLOSED_UNCONFIRMED_NO_RESPONSE`。如果服务在整个询问窗口没有运行，恢复检查仍可直接关闭，并不证明患者收到过询问；关闭伴随任务及参与窗口收束。（F10，L290–306；流程图 L109–117）

**审查判断。** 区分“未确认关闭”和“成功解决”是必要的，但并未解决另一个问题：为什么可以停止仍可能需要的协调？患者沉默、提示未送达、服务停机和现场确实结束不是同一事实。原稿对该问题的显著程度不足，不应仅作为 Q10 的一个普通待确认项。

**风险推演，非实测。** 服务在第 29 分钟停止，在第 36 分钟恢复；患者可能从未看到询问，但恢复检查可能关闭事件。另一情形是响应者仍在行动，患者却没有操作手机，原始时限仍可能触发收束。

**补充要求。** 明确最初 30 分钟从哪个时间起算；询问未送达、已送达未回答、响应者仍报告在场、服务中断后恢复分别怎么处理。若业务决定仍要停止协调，必须明确停止的含义、告知、资源交接和恢复方式，不能以修改状态名称代替该决策。

**复核用例。** 询问前宕机跨越截止时间后恢复；询问发布失败；患者未回答但响应者持续提交有效进展。预期结果必须引用批准的业务决策，不由开发者自行选择。

### RV-02 触发范围本身需要批准，不是写出代码条件就结束

**原稿事实。** 120 秒跌倒上下文内，明确需要帮助可以触发；未回答时仅新的外拨观察可以触发；既未回答又未观察到新外拨，窗口到期则不建立事件。材料也明确没有普通用户正式手动 SOS 入口，外拨观察不证明拨打了急救号码。（L23、L51–53、L74–84、L143–159、L502–505）

**审查判断。** 这不自动构成代码错误，但决定了产品覆盖范围。必须明确：无法回答且没有被观察到外拨的情况，是否就是本期不覆盖的情况；无法观察系统事件时如何告知能力不可用。不能把“跌倒相关求助”宣传或理解为任何跌倒都能触发。

**补充要求。** 为“跌倒有/无、回答需要/不需要/未回答、外拨有/无、观察迟到、上报离线”写出决策表。明确系统能力的实际验证方式。不要未经批准自动新增手动 SOS，也不要把观察到外拨改写成已经获得专业急救服务。

### RV-03 Watch 终态清理是闭环缺口，不是普通代码整理

**原稿事实。** `clearActiveEvent()` 有实现但没有生产调用者；触发上报不使用返回事件 body；备用上报失败统一转为重试；当前 WCSession 封包不包含终态。（R02，L701–707；通信表 L556–563）

**审查判断。** 后端结束不能只结束 iPhone 页面。Watch 需要取得权威终态，并区分暂时网络错误、授权失效和事件已经结束，否则可能继续保留旧活动标记和旧队列。

**补充要求。** 明确 Watch 独立恢复接口或响应中的终态语义；失联时不能承诺设备立即知道远端结束，但恢复后必须收敛。清理时区分合法历史待确认数据和终态后新产生的业务数据；不能把所有 HTTP 409 直接当作删除队列指令。

**复核用例。** iPhone 结束事件时 Watch 不可达但可联网；Watch 离线后重启；旧位置仍待 ACK；终态恢复后再次出现新的跌倒。分别核对本地状态、权限、队列和后端记录。

### RV-04 定位时间保真与主备切换需要一起补审

**原稿事实。** Watch 初始快照使用缓存位置，未独立保存实际 fix 时间，后端使用跌倒或外拨时间标记快照。备用上报的本地启动条件又要求 iPhone 不处于“已激活且即时可达”；后端采用备用位置则还需连续 10 秒没有有效手机 P。（R16，L814–820；F04，L187–195）

**审查判断。** 第一处是位置事实失真的风险：旧坐标不能靠新的事件时间成为新位置。第二处是原稿没有单列的故障覆盖问题。

**新增风险推演，非实测。** iPhone 与 Watch 仍能即时通信，但 iPhone 的定位或后端上报路径异常；Watch 自己有网络及合格定位。按原稿给出的条件，Watch 可能不启动备用，后端即使已经满足 10 秒条件也没有备用数据可选。必须回查完整源码确认是否另有路径覆盖。

**补充要求。** 独立保留定位发生时间、事件观察时间和后端接收时间。用状态表组合检查 WCSession 可达性、后端最后有效 P、Watch 网络与位置质量，明确是否需要后端认可的位置健康信息。报告中的 600 秒、200 米、120 秒是开发默认参数，不代表已经验证的生产配置。

**复核用例。** 触发时只有陈旧缓存位置；WCSession 可达但手机不上报；手机持续发送不合格 P；主备恢复竞争和迟到样本。不得伪造采样时间来使测试通过。

### RV-05 对象可见不等于所有字段可见，撤销身份必须影响已有连接

**原稿事实。** 待接受候选人的事件投影被裁剪，但 timeline 在可见性检查后返回内部记录，可能包括帮助回答、外拨观察及稳定用户标识。Socket 仅在握手与令牌到期处检查身份生命周期，logout 没有主动断开相关服务端连接的链路。（R01，L693–699；R17，L822–828）

**审查判断。** 应优先于一般性重构处理。仅隐藏页面或要求正常客户端主动断线，不能构成服务端授权边界。材料没有证明已经实际泄露患者精确坐标，也没有提供实际攻击或线上泄露证据，不能扩大结论。

**补充要求。** 列出患者、候选人、参与者、退出者、已撤销会话和授权操作方的逐接口、逐字段及逐事件权限矩阵。内部审计记录与恢复快照分离；定义会话撤销生效时限及存活连接处理方式。

**复核用例。** 候选人直接请求 timeline；退出事件但账号仍有效的用户读取/订阅旧事件；会话撤销后保持原 Socket；跨用户访问与旧事件回放。测试应检查实际响应字段和后续通知，而不是只看 UI。

### RV-06 AED 是跨事件实体，失败、持有、交接和归还不能止于任务取消

**原稿事实。** 找不到替代 AED 时不会保证立即生成前往患者的新任务；携 AED 退出没有完整交接闭环；同一 AED 的排重主要局限于单个事件，没有完整跨事件占用和归还模型。（Q07–Q09，L255–272；R06–R07，L733–748）

**审查判断。** 存在三个相互关联的问题：资源失败后人该做什么；人退出后 AED 在谁手里；其他事件何时能够再次分配同一台物理设备。事件结束或任务取消不等于现实中的 AED 已经回到原位。

**补充要求。** 分开定义任务生命周期和物理 AED 生命周期。明确分配、取得、不可用、交接、退出、事件结束和恢复可取得的关系。无替代时必须有明确下一步；但立即前往患者、继续等待或其他动作仍需业务批准，不能由本审查擅自补为既有需求。

**复核用例。** 两事件同时选择一台 AED；取得后退出；持有时事件结束；交接中断；在未确认恢复可取得时产生另一事件。不得简单按固定超时释放现实中仍被携带的设备。

### RV-07 已接受人数不代表有效行动人数；登出与权限降级需按阶段定义

**原稿事实。** 失联自动补位链路未完整形成；logout 不等价于 exit/end；业务主界面要求四项同意及定位、通知门槛；材料将活动期间登出、撤回同意和权限丢失列为 Q12。（R08–R09，L750–764；F01，L125–141；Q12，L417）

**审查判断。** 可能出现人已无法继续操作、系统仍把他算作有效参与者的情况。还需补查另一条路径：活动中的患者若失去通知或精确定位权限，能否继续查看事件以及提交误报/结束等核心操作？材料不足以确认当前 UI 行为，不应直接断言一定被挡住。

**补充要求。** 分开定义进入待命资格、接受响应资格、活动中能力下降、患者操作权限、数据上传权限。将“已接受”“当前通信可用”“已出发”“已到场”等统计语义明确区分。既不能擅自把登出改成患者获救，也不能删除凭据后丢失必要收束命令。

**复核用例。** 唯一响应者登出；多人参与中的一人失联；取得 AED 后掉线；患者撤销通知或定位权限；离线撤权后重新登录。结果以批准的阶段规则为准。

### RV-08 eventId 幂等不能替代现实事件与账号的仲裁

**原稿事实。** 相同 eventId 去重，不同 eventId 仍可创建；客户端只选择一个 currentEvent 展示。（Q03，L161；R11，L774–780）

**审查判断。** 多个不同标识可能代表同一个人的同一段求助，也可能代表后续新情况。两者如何处理必须有业务规则；单个 UUID 的去重不能自行完成此判断。

**补充要求。** 明确同一用户已有活动患者事件时的新触发政策，以及结束与再次触发交错时的处理。若允许并行，必须同时设计客户端选择、位置发布与单独终结；若不允许，应明确拒绝、合并或追加观察的语义。

**复核用例。** 同一用户两个不同 ID 并发；多设备重放；旧事件结束响应丢失后出现新触发；患者优先时原响应任务收束。

### RV-09 正式触发、身份和通知链路是前提，不是由模拟测试代替

**原稿事实。** 实际组成根未接入完整的短信及 Watch 证明供应商；APNs 闭环未完成；原稿不主张系统事件可观察性、双机完整流程及后台场景已经通过。已有 124 项测试及单机蜂窝记录只是原稿读取的历史材料。（R05、R14；L727–731、L798–804、L840–851）

**审查判断。** 这些是正式能力验证门禁。缺实现、待配置和待验证应分别登记；不能把测试事件创建、前台 Socket 成功、健康检查通过等价为真实使用链路成立。

**补充要求。** 为正式身份、Watch 绑定、系统触发、后台通知、接受和任务推进建立独立证据项，记录构建、配置、设备状态、运行日志及失败情况。若限定为受控原型，应显式写清范围，不得混为正式验收。

**复核用例。** 使用正式依赖完成一次端到端闭环；分别验证前台、后台、锁屏、离线恢复等已经纳入范围的状态。不能承诺无法由证据支持的绝对送达或固定后台频率。

### RV-10 位置完整性与容量目标需要共同设计，但不必据此立刻全面换栈

**原稿事实。** 后端 read/transact 复制、校验整个状态；本地队列整体 JSON 读写；没有全参与窗口完成协议。原稿目标量级示例为 2000 个参与者、60 分钟，每人每秒一条、每五条一批，约 400 批/秒及 720 万条记录；该数字只是推算。（R04、R12，L717–723、L782–788；L849–853）

**审查判断。** 历史量会进入后续读写的成本，不能只压测空库和健康检查。已收到的记录无重复不等于所有应该收到的记录都存在。另一方面，仅凭 SQLite、单进程或大文件不能断言当前小规模场景已经性能失败。

**补充要求。** 先固定本期容量目标、延迟目标、数据留存、断网积压上限和恢复要求，再测全量历史下的关键命令。将实时有效位置、历史证据和重试队列的职责明确分开。完成协议应区分未知、待补传、已完成、最终缺失，不得通过静默丢弃记录让队列看起来正常。

**复核用例。** 大量历史后的接受/退出/结束；一小时参与数据积累；长时间离线后补传；存储不足；重启与备份恢复。容量结果必须注明负载与数据规模，而不是仅给一个总 RPS。

### RV-11 邀请回执与用户决定不能留下不一致的硬门槛

**原稿事实。** 手机要求 VIEWED 回执已经确认，后端 respond 没有相同要求；邀请仅 30 秒有效；重试标识和结束入口也存在不一致。（Q16、R18、R10，L220–228、L766–772、L830–836）

**审查判断。** 弱网时可能出现用户已经看到并作出决定，却因为统计回执没有确认而被界面阻塞。硬业务门槛应统一由权威端执行；统计记录不应被无意提升成另一套业务规则。

**补充要求。** 明确 VIEWED 是资格条件还是观测事实；定义截止时刻、重试标识、首次成功响应丢失及已有终态的返回语义。不要通过伪造查看回执或一律重发新 ID 绕开问题。

**复核用例。** 查看 ACK 延迟、接受先到、到期边界、相同意图重复、内容冲突和首次响应丢失。预期必须统一前后端。

## 4. 原稿 18 项风险的逐项复核与排序建议

下列是建议处理类别，不是已复现漏洞分级。门禁含义需与项目阶段对应，不能把“原型可运行”与“正式使用可批准”混为一谈。

| 原编号 | 本次意见 | 建议处理类别 |
| --- | --- | --- |
| R01 内部 timeline 暴露范围 | 保留；需字段级及接口级授权证据，不能只隐藏 UI | 正式使用前的权限门禁 |
| R02 Watch 终态链路缺失 | 保留；升级为跨端生命周期闭环问题 | 核心闭环门禁 |
| R03 AppStore 状态集中 | 保留为维护和正确性风险；无具体路径证据不能称已复现错误 | 先回归测试与状态归属，后逐步拆分 |
| R04 全状态复制与单写 | 保留；当前吞吐尚未测定，集群能力不可据此推导 | 声明容量目标的验收门禁 |
| R05 非统一可靠投递/APNs | 保留；关键提示需期限和失败策略，REST 恢复不是及时提醒的替代 | 正式通知能力门禁 |
| R06 路线、失败重派、交接 | 保留，但拆成明确业务子问题，避免只更换地图服务 | 业务冻结及流程闭环门禁 |
| R07 跨事件 AED 争用 | 保留；补事件结束后持有与归还语义 | 物理资源一致性门禁 |
| R08 失联补位 | 保留；通信状态与参与资格、人数、任务需联动 | 业务冻结及异常闭环门禁 |
| R09 登出和业务参与脱节 | 保留；补活动患者的权限降级与必要操作可用性 | 撤权及异常闭环门禁 |

## 6. 需要新增的评审材料

### 6.1 需求—实现—差异—验收追踪表

每项关键规则至少包含：规则 ID、已批准需求及出处、当前实现与代码证据、差异、建议、决策状态、验收用例。缺少批准依据的条目保持未决，不引用代码本身作为业务批准来源。

优先覆盖 120 秒触发、35 分钟首次创建截止、30＋5 分钟关闭、目标 3 人、无人数硬上限、拒绝或过期不再邀请、唯一响应者三次确认、AED 分工比例及权限门槛。上述数值和行为均出现在原稿，但不因此自动成为已批准规则。

### 6.2 时间与配置表

为每个时间阈值写明：用途、计时起点、权威时钟、等号边界、离线/重启补算规则、开发默认值、实际部署值、批准依据和测试。

必须区分定位采样时间、事件发生时间、后端接收时间、命令首次提交时间和重试时间。实际部署值未读取则标记未知，不用开发默认值代替。

### 6.3 完整状态转换及权限矩阵

原稿任务图已注明只展示代表性取消边，因而适合阅读但不能直接代替全量实现合同。（L344–368）

转换表应覆盖事件、招募、邀请、任务、参与关系、患者位置来源以及跨事件 AED。每项填写原状态、命令/事实、主体、前置条件、目标状态、原子修改、外部通知、重复返回、冲突返回、失败恢复和验证用例。特别检查多个状态机的组合是否允许，而不只检查单个枚举是否合法。

### 6.4 可复核源码证据

对关键事实提供固定快照、仓库相对路径、行号范围、符号名、必要片段及调用链。对“没有调用者”一类否定性结论写明检索范围、活动 target、排除文件和验证方法。测试源码、测试运行和运行日志分别标记，不互相替代。

### 6.5 关键架构决策记录

当前架构说明不仅要列“用了什么”，还应解释选择依据和适用边界。至少记录单进程协调、单写事务、位置事实与实时位置的关系、通知与恢复策略、Watch 独立运行边界、物理资源一致性，以及容量达到何种条件才迁移存储或部署方式。

无需为形式完整立即改成微服务，也无需把所有维护风险升级成当前运行故障。反过来，也不能以“毕设”为由默认取消尚未明确调整的容量和完整性要求。

## 7. 下一轮评审的完成条件

下一版应能清楚回答：哪些规则已经批准，哪些待决；当前实现哪些符合、哪些不符合；关键问题由哪一条业务决策及哪一项架构改动解决；采用什么用例证明修正；哪些能力仍受外部系统和实际设备验证限制。

建议顺序：

1. 先冻结会改变行为的业务选择：触发覆盖、无回答关闭、多事件、人数、失联、退出与 AED。
2. 再批准权限、定位时间、Watch 终态、可靠命令与资源一致性的修正设计。
3. 完成正式身份、系统事件、通知和双机闭环验证。
4. 根据已固定的目标完成数据完整性、积压、历史量、容量与恢复验证，再决定存储迁移和模块拆分。

以上是处理顺序建议，不表示任何修复、测试或部署已经执行。
