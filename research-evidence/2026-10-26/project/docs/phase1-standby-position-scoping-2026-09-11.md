## 1. 更正：我的 fsync 推导是错的，GPT-6 是对的

GPT-6 指出：`persistChanges()` 在发现无变化时，会在创建并执行 SQLite 写事务之前返回，
因此 2.1 ms 的 no-op **不包含** fsync，不能用来推导 300–500 次/秒。
**已在源码中确认成立**：

```ts
// backend/src/store.ts
1448  private persistChanges(previous, next): void {
1452    const before = this.flattenedState;
1453    const after = flattenState(next);              // ← 仍然全量 flatten
1454    if (before.size === after.size) {
1455      let unchanged = true;
1456      for (const [identity, item] of before)
1457        if (after.get(identity)?.payload !== item.payload) { unchanged = false; break; }
1462      if (unchanged) return;                        // ← 在这里就返回了
1463    }
1464    const upsert = this.database.prepare(...);      // ← 从未执行
1472    const write = this.database.transaction(...);   // ← 从未执行
1486    write();                                        // ← 从未执行，因此没有 fsync
```

（行号已核对。）另外 GPT-6 指出我同一份文档里"旧实现的 no-op 已经省掉 SQLite 写入"
与"2.1 ms 就是 fsync"自相矛盾——**这个矛盾确实存在于我的文档里**，是我的错误。

**结论：撤回"300–500 次/秒由 2.1 ms no-op 推出"这一结论及其论证。**
下面用真实变更事务重新测量，并且**只把它当作预期值，不作为承诺**。

## 2. 重测：真实提交成本

新脚本 `backend/scripts/loadtest/probe-commit.mjs`，2026-09-11 在 Azure 联调机实测。

### A. 裸 SQLite 提交成本（WAL，每次提交 1 行 upsert，n=200）

| `synchronous` | 中位 | p95 | 最大 | 提交/秒 |
| --- | --- | --- | --- | --- |
| **FULL** | **2.88 ms** | 4.60 ms | 8.32 ms | **347** |
| NORMAL | 0.02 ms | 0.03 ms | 0.75 ms | 66,410 |
| OFF | 0.02 ms | 0.03 ms | 0.06 ms | 66,454 |

**同步成本（FULL − OFF）≈ 2.87 ms/commit。** NORMAL ≈ OFF，证实 WAL 下 NORMAL 提交不 fsync。
p95 4.60 ms / max 8.32 ms 说明提交有波动（含 WAL 检查点），持续吞吐必须看分布而不是中位。

### B. 存储层真实事务（251 实体 / 0.08 MB）

| 操作 | 中位 | 吞吐 |
| --- | --- | --- |
| no-op（无 SQLite 提交） | 0.92 ms | 1,087/s |
| **1 个实体变更（真实提交）** | **4.04 ms** | **248/s** |
| 50 个实体变更（真实提交） | 5.16 ms | 194/s |
| 差值 = 真实提交成本 | **3.12 ms** | — |

### 修订后的预期（不是承诺）

| 阶段 | 写吞吐 | 主导因素 |
| --- | --- | --- |
| 现在 | ~10 次/秒 | 全量校验 CPU |
| Phase 1 后 | **~250–350 次/秒（预期，须同环境实测确认）** | **fsync（存储设备属性，不是代码属性）** |

**一个对后续决策很关键的新发现**：1 个实体变更 4.04 ms，**50 个实体变更只要 5.16 ms**——
写入量增加 50 倍只多 1.12 ms。**提交成本几乎与行数无关，完全由 fsync 主导。**
这意味着**批量提交（group commit）的余量很大**，是"保住 `synchronous=FULL` 同时拿回吞吐"的正解：
把队列里已排队的多个业务事务合并成一次提交，**提交完成后才 resolve 全部 promise**，
客户端仍只在持久化后才收到成功。建议把它从 Phase 3 提前到 Phase 1 完成后立即评估，
而不是等容量报告出来再说。

关于 `synchronous` 的取舍现在也可以量化了：FULL 2.88 ms vs NORMAL 0.02 ms = **137×**。
但**同意 GPT-6，本批不改**——本系统的位置证据是"服务端 REST ACK 后才允许客户端删除"，
ACK 之后因掉电丢失就是真丢失，直接违反证据保留要求。NORMAL 只有在同时改 ACK 语义时才可讨论。

## 4. 新发现：这条路径的 Δ 不是"1 台设备"，事务内仍有 O(事件) × O(投递) 扫描

这是我在核对 Phase 1 首个用例时**新查到的**，GPT-6 的方案与我的上一版评审都没有点到。
`PUT /api/v2/me/responder-position` 的处理函数 `updateResponderPosition`（`service.ts:3187`）
在事务内（`service.ts:3201` 起）并不只碰该设备：

```ts
// service.ts:3262-3276  事务内部
const updates: RecruitmentUpdate[] = [];
if (position.applied) {
  for (const event of Object.values(state.events)) {          // ← 遍历全部事件
    const refreshed = this.refreshRecruitmentForEvent(state, event, this.now());
    if (refreshed.changed) { updates.push(this.recruitmentUpdate(...)); }
  }
}
```

而 `refreshRecruitmentForEvent`（`service.ts:4599`）内部：

```ts
4609    const previousAudience = coordinationAudienceDeviceIds(state, event);
4610    if (event.state !== "ACTIVE") {
4611      return { changed: false, ... };                         // ← 已结束事件：白算了一遍 audience
4612    }
...
4620    for (const delivery of Object.values(state.deliveries)) {  // ← 遍历全部投递
4621      if (delivery.eventId !== event.id || !pendingDeliveryStatuses.includes(delivery.status)) continue;
```

**成本是 `O(事件数) × O(投递数)`。** 按 P20 的 100 并发事件 / 2,000 参与者投递，
**每次位置上传有约 20 万次迭代**，而这发生在写事务内部、占着单写者队列。

三个直接结论：

1. **只做实体级事务，这条路径仍然不是 O(Δ)。** 框架成本消掉了，业务扫描还在。
   所以 GPT-6 那条"处理实体数 ≤10"的验收项**当前无法达到**，
   而且 GPT-6 提醒的"只统计写集合会漏掉扫描"正好命中了这个情形。
2. **`coordinationAudienceDeviceIds` 在 `ACTIVE` 守卫之前无条件计算**——已结束的事件也要白算一遍
   `previousAudience`。而调用方（`service.ts:3266-3273`）**只在 `refreshed.changed` 为真时才用它**。
   所以这一项可以改成惰性计算，是**零风险的免费优化**。
3. 要把这段变成 O(Δ)，需要两个索引 + 一次收窄：
   - `deliveriesByEventId`：把 `Object.values(state.deliveries)` 收窄为该事件的投递
   - **事件相关性索引**：该设备的位置变化只可能影响"搜索圈覆盖到该设备新位置"的活跃事件，
     而不是全部事件。需要按患者位置 + 当前招募半径做候选筛选（至少先做便宜的包围盒预筛）
   - `coordinationAudienceDeviceIds` 惰性化

**建议把这三项明确写进 Phase 1 范围**，否则第一个用例就会变成"接口改了、内部仍在扫描全部"，
而这正是 GPT-6 自己警告的假优化。

## 5. 我还有的疑问（需要 GPT-6 或实测回答）

### 疑问 1：影子校验与 Phase 2 不兼容，且"提交前全量校验"本身需要物化全量候选状态

GPT-6 建议开发/测试模式下**提交前**跑旧版完整校验 + 历史前后对比。
比我的"提交后"正确，但有一个结构性矛盾：

**要跑 `validateSnapshot(候选状态)`，就必须先构造出完整的候选状态**——
也就是把 change-set 应用到一个全量副本上，再全量校验、再全量比较历史。
**这正是我们要消除的 O(E)。** 在 Phase 1 期间可以这么做（反正全在内存，且只在开发/测试路径），
但**Phase 2 把历史移出内存之后，就无法再物化"完整候选状态"了**——
影子校验这种形态会自然失效。

所以我认为需要现在就明确：

- 影子校验是 **Phase 1 的临时安全网**，不是长期的等价性保证；
- 长期等价性证据应改为"**隔离库上新旧实现跑同一组命令、比较结果与最终持久化内容**"
  （GPT-6 也列了这一条，但没说明它是影子校验的**替代**而非补充）；
- **Phase 2 开工前必须完成这个切换**，否则会出现在"历史已出内存"的架构上
  还依赖一个"必须全量物化"的校验器的尴尬局面。

请确认这个理解，并把"影子校验 → 新旧对照"的切换点写进阶段边界。

### 疑问 2：启动加载路径的成本，我漏得比 GPT-6 指出的更严重

GPT-6 要求 Phase 2 覆盖"启动不再一次性重建全部历史对象"。我核对后发现问题更大：
启动路径上状态树被**构造了多份**：

| 步骤 | 代码 | 产生的东西 |
| --- | --- | --- |
| 1 | `stateFromItems`（`store.ts:1247`）逐行 `JSON.parse` 全部 payload | `raw` 全量对象树 |
| 2 | `validateState(raw)`（1268）→ `normalizeState` 内 `structuredClone`（243） | `state` 第二份全量对象树 |
| 3 | 构造函数 `this.state = cloneState(initialState)`（1298） | 第三份全量对象树 |
| 4 | 构造函数 `this.flattenedState = flattenState(this.state)`（1299） | 第四份：全量 JSON 字符串副本 |

**即启动时同时存在 3 份对象树 + 1 份字符串副本。** 这在 7.2M 条证据的规模下
不只是慢，而是**启动即 OOM**。而且第 3、4 步对刚加载完的数据是纯浪费。

建议把这一项从"Phase 2 的一条要求"提升为 Phase 2 的**首个验证目标**，
因为它是唯一一个"不改就一定崩"的项——运行期优化做得再好，重启也会失败。
请确认是否需要为它单列一个更早的交付点。

### 疑问 3：reconcile 的真实成本和调用率，建议 Phase 1 期间就插桩

我接受"8×10⁷"是未经验证的推算。但代码事实仍然成立：
`server.ts` 里 3 处 `isAuthorized`（每次 Socket 连接至少各走一遍）、
`service.ts` 里 5 处 `emitToDevices`，每次都会触发 `reconcile()` 的 O(C) 全量重算。

我无法在不实测的情况下判断 Phase 1.5 有多紧迫。建议：
**在 Phase 1 的插桩里顺带统计 `reconcile()` 的调用次数与耗时分布**（按连接数分档）。
这样 Phase 1 结束时就能用真实数据决定 Phase 1.5 的优先级，而不是靠推算争论。
如果 GPT-6 认为可以现在就估一个上界，请给出估算方法与置信区间。

### 疑问 4："Phase 1.5 的目标值"是什么

GPT-6 给 Phase 1 定了 200 次/秒的验收目标，但 Phase 1.5（实时层）只给了定性描述
（"定向发送的开销应随目标连接数增长，而不是随全站连接数增长"）。
建议同样给一个可测门槛，例如：

- 2,000 条连接下，单次定向发送到 10 个设备的耗时，与发送到 1,000 个设备的耗时之比，
  应接近 10:1,000 而不是 1:1；
- 5,000 条连接下，`isAuthorized` 的单次耗时不超过 100 条连接下的 X 倍。

否则 Phase 1.5 会缺乏合并条件。

### 疑问 5：验收目标 200 次/秒的余量

实测 1 实体真实提交在 251 实体库上是 **248 次/秒**。200 的目标可达，但余量只有约 20%。
更重要的是**它无法区分两种结果**：

- 好的结果：框架成本已消除，瓶颈是 fsync（差值收敛到 ~3 ms）
- 坏的结果：框架成本仍在，只是比原来小

建议把验收项拆成两条：
1. 吞吐 ≥ 200 次/秒；
2. **no-op 与真实变更的耗时差收敛到 ~3 ms 量级**（即证明剩余成本是 fsync 而非框架）。

第 2 条才是"全库遍历已消除"的真正证据，第 1 条单独不成立。

## 6. 修订后的 Phase 1 范围（建议直接交给开发）

**范围**

1. 受控实体事务接口 + 自动 change-set（禁止业务直接改整棵树）
2. 校验三拆：`migrateLegacyState` / `validateSnapshot` / `validateChangeSet`
3. 增量持久化：只序列化与保存变更实体；**相同内容不产生任何 SQL 写入**
4. 空变更提前返回（在 flatten 之前，而不是在 flatten 之后）
5. **本条路径的查询索引**：
   - 消除 `store.ts` 事务内的全量遍历（框架层）
   - 消除 `service.ts:3283` 事务外的 `store.read` 全量克隆（仅为算 `positioningTier`，
     事务内已有 device，直接取即可）
   - `deliveriesByEventId` 索引
   - 事件相关性筛选（先做包围盒预筛）收窄 `service.ts:3264` 的事件循环
   - `coordinationAudienceDeviceIds` 改为惰性计算
6. 开发/测试模式：**提交前**跑旧版完整校验 + 历史前后对比
7. 插桩：实体扫描 / 访问 / 复制 / 校验 / 序列化 / SQL 写入 / 队列等待 / 实际提交次数，
   以及 `reconcile()` 调用次数与耗时分布

**不变量（不得降低）**：身份与幂等契约、证据不可改写、位置记录频率与秒槽要求、
状态迁移规则、`synchronous=FULL` 与 WAL、救助流程。

**不做**：实时层改造、其余索引迁移、历史分层、`synchronous` 变更、group commit
（group commit 在 Phase 1 完成后立即评估，不推迟到 Phase 3）。

**验收**

| 项 | 要求 |
| --- | --- |
| 处理实体数 | 纯待命单设备场景；**分别**统计扫描/访问/复制/校验/序列化，均应为常数 |
| 历史无关性 | 固定在线数/请求率/数据构成/payload 大小，历史 1k→100k 实体，P95 变化 < 20%，重复测 |
| 吞吐 | ≥ 200 次/秒，用真实新位置与合法新请求标识，同时满足 P95；**并证明剩余成本是 fsync**（差值收敛到 ~3 ms） |
| 空变更 | 在隔离测试中测本条操作：提交数 = 0，且无全事件扫描、无无意义 revision 更新 |
| 幂等 | 同 ID 同内容 → 返回既有结果且无 UPDATE；同 ID 不同内容 → 拒绝 |
| 正确性 | 影子对照 + 新旧对照 + 非法历史修改 + 回滚 + 重试 + 重启恢复全绿 |
| 持续性 | 报告内存峰值、队列等待、WAL 大小、长时运行结果，不能只报短时最高吞吐 |

**性能压测必须关闭影子校验，并在报告中标注开关状态**，否则测到的仍包含全量检查成本。
