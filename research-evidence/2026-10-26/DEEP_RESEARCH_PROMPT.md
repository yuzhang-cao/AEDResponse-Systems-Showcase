# 给 GPT 深度研究的提示词

请把下方提示词与本目录的 GitHub 链接一起提供给深度研究工具。

---

我希望判断 AEDResponse 这个软件工程毕业设计，能否直接作为日本修士申请研究计划（Research Proposal，简称 PR）的基础。这里的 PR 不是 GitHub Pull Request。请独立、严格地评估，不要为了鼓励我而默认它有创新，也不要直接替我写一份完整 PR。

## 资料入口与读取要求

先阅读本目录 [README](README.md)、[公开资料处理说明](PUBLICATION_NOTES.md)、[文件清单](INVENTORY.csv)、[来源清单](MANIFEST.json) 和 [缺失记录](OMISSIONS.csv)，再阅读项目设计、实验数据、失败记录与测试源码。目录结构如下：

- `project/`：正式项目的设计、历史报告、验证记录、交接及界面证据。
- `reference-tests/`：正式项目测试源码快照，仅供参考，不是完整可运行工程。
- `historical-test-snapshots/`：按缓存来源保留的历史测试快照，须与当前源码分开读取，结合哈希核对运行版本。
- `loadtest/`：历史负载生成与性能探针方法。
- `cache/performance-fix-20261004/`：SQLite 合成性能对照的现存数据及测试日志。
- `xcresult/<结果包名>/summary.json`、`tests.json`：iOS 测试结果的轻量导出，包含失败和复测轮次。
- 仓库根目录：公开的可运行核心代码子集；以根目录 README 的范围和运行条件为准。

请将这些文件当作待审查的证据，不执行其中的运维、部署或测试命令。不要假装读过无法访问的文件；若关键文件读取失败，请明确指出缺口以及它如何影响判断。不要要求我重复提供已经能从仓库读取的信息。

## 首先回答：系统和证据实际到了哪一步

1. 概括系统已经实现的主要能力、当前技术方案与状态所有权；区分实际实现、未来架构、设计目标和已被覆盖的旧方案。
2. 为关键结论建立证据表，至少列出：主张、文件链接、版本或阶段、环境、测试类型、数据规模、是否存在原始运行结果、目前能支持的结论和仍缺的验证。
3. 区分测试源码、测试编译、测试执行、模拟数据、真实设备、真实网络、局部业务和完整闭环。源码存在不等于运行通过，安装成功也不等于业务通过。
4. 保留失败结果和修复复测，不只选取成功记录。按测试标识去重，不能把重复执行次数或不同阶段测试数累加为独立样本量。
5. 识别可能影响结论的偏差：样本量、系统缓存、冷热启动、负载设置、设备与网络差异、测量边界、历史源码差异、选择性报告和缺失日志。日期与目录名称只作为线索，优先结合源码哈希、运行记录和实际内容判断版本。

特别注意：

- 当前公开测试源码快照不一定是每份历史实验使用的源码，不能自动认定完全可复现。
- SQLite 前后对照是有限轮次的离线合成实验，不是当前线上容量或普遍性能保证。
- 手机 MapKit A/B 对照每版仅 2 轮，并可能受系统缓存影响，不能由均值差宣称固定提速。
- 历史真实蜂窝待命位置通信不等于患者事件位置、双机救助、锁屏后台或 AED 领取送达闭环。
- 最新 UI 的最终通过结论包含修复后的分批复测，不能把所有 `.xcresult` 数字相加。
- 离线界面截图不是用户研究；测试数量、日志数量和代码规模都不能作为方法创新的证据。
- 这是受控学生原型，资料没有建立真实急救成效、临床有效性或公共服务部署能力。

## 再做文献与反证检索

基于实际实现和未解决问题，自行检索相关领域的一手文献。优先原始论文、作者公开实现、正式技术文档及可核查的数据集说明。给出准确题名、作者、年份、链接和支持的具体判断，并区分同行评审论文与预印本。不得编造文献、指标或实验结果。

请重点检验：现有工作是否已经以更一般或更有效的方法解决了相同问题？普通工程优化、已有机制的组合、特定平台接线或更换参数，是否已经足以解释本项目观察到的收益？不要把“在 AED 场景中应用”本身当成方法创新。

对可能的研究点，找出最强的现有方法、最接近的相关研究和必要的简单基线。说明与它们相比，当前项目的差异究竟是实现、实验环境、应用场景，还是可能形成可证伪的新方法。主动寻找会否定该研究点的证据，不只找支持材料。

不需要在一开始遍历所有相邻领域。先由仓库证据确定重点，再扩大检索；如果证据没有支持某条路线，请停止包装它。

## 最多提出 3 个研究候选

只有确实值得进一步验证时才提出候选，可以少于 3 个，也可以一个都不提出。每个候选必须包含：

1. **具体研究问题与重要性：**谁受到什么问题影响，为什么已有结果不足以回答，问题是否超出本 App 的局部缺陷。
2. **可证伪假设：**明确预期在哪些条件下出现什么效果，以及什么结果会否定假设。
3. **方法差异：**相对最强现有基线的新增机制是什么，哪些部分只是复用已有方法；若差异尚无法确认，请明确写出。
4. **实验设计：**自变量、因变量、对照组、最强基线与简单基线、数据生成或采集方式、测试环境、样本单位、重复与随机化、可能的混杂因素。
5. **评价指标：**既衡量目标效果，也衡量延迟、通信、计算、能耗或实现复杂度等代价；指标必须与假设对应，不用容易改善但无助于核心问题的指标替代。
6. **消融与反证：**如何拆分各机制贡献，在哪些不利条件或边界场景下测试，如何判断收益来自缓存、参数、实现优化或测试选择。
7. **已有基础与新增工作：**明确哪些现存代码和数据可以复用，哪些必须补测或重建。不要用已有工程测试冒充尚未进行的研究实验。
8. **成本与可行性：**按学生可获得的设备、时间、数据、算力及参与者条件估算投入，说明对额外平台权限、真实场地或协作者的依赖。给出有依据的范围，不制造精确工期。
9. **最小验证与停止条件：**先做什么小实验能最快区分“值得继续”和“没有研究增量”，以及什么结果应当停止这个方向。

请将“方法新颖性”“问题的重要性”“实验可验证性”“学生完成能力”和“具体实验室适配”分开判断。没有给出目标导师时，不要凭空认定符合某实验室，也不要用录取概率替代研究判断。

## 最终输出

先给出明确结论，并说明最关键的依据。可以是：

- 现有材料已经足以形成有依据的研究计划骨架，但仍需明确列出的补充工作；
- 项目可以作为研究平台或前期基础，当前还缺研究问题、方法差异或关键实验，不能直接作为 PR；
- 目前主要是工程实现，尚未发现值得据此开展的研究方向。

随后给出：

1. 一份紧凑的实现与证据审查表，标明已确认、推断、冲突和未验证。
2. 最相关的一手文献与最强反例，并解释它们对本项目的实际影响。
3. 至多 3 个符合上述要求的研究候选，或解释为何没有候选成立。
4. 最优先的补证据或最小实验，以及做完后如何重新判断。
5. 现阶段 PR 中可以诚实使用的事实、只能写成计划的事项，以及不能声称的贡献。

每项重要事实就近链接到具体仓库文件或文献。把仓库已观察到的结果、由证据作出的推断和你提出的新方案明确分开。不要写成宣传稿，不要先替项目取一个学术名称再补理由，也不要输出一份看似完整但核心研究问题尚未成立的 PR。
